# SA-MP client Luna pilot audit

**Scope:** `src/client/net/gangzonepool.cpp` and `src/client/net/textdrawpool.cpp`, plus their complete headers and the `CTextDraw` constructor/destructor contracts in `src/client/game/textdraw.*`.
**Authority:** `GTA Sa samp_clone/samp.dll.official`, reference SHA-256 `bccdb297464bd382625635be25585df07a8fa6668bc0015650708e3eb4ffcd4b`.
**Method:** Read both target source files and headers in full. For each exact candidate start, read the complete address-named pseudocode through its END FUNCTION marker and invoke `tools/read_reference_function.py client 0xVA --asm` (official binary, on demand). Cross-check index body ranges, body-start metadata, and incoming static references. Every subprocess was bounded by `subprocess.run(..., timeout=...)`. No reference corpus was regenerated. Imported comments were used only to nominate VAs (`comment RVA + 0x10000000`), never as proof.

## Per-function evidence

### `src/client/net/gangzonepool.cpp`

All starts below are exact `assembly_entry` candidates in `docs/asm/pseudocode/samp.dll/index.tsv`; each complete pseudocode body and direct official disassembly was read. Exact body ranges are reported by the reader as shown. The client class uses `this` in ECX; WORD IDs are zero-extended from stack, DWORD/float arguments are 32-bit stack values. Direct callsites in `samp.dll.official` point to the relevant RPC methods: 0x1001cb40 (create), 0x1001cc60 (delete), 0x1001cd10 (flash), 0x1001cdd0 (stop flash); these map in clone dispatch to `ScrGangZoneCreate`, `ScrGangZoneDestroy`, `ScrGangZoneFlash`, `ScrGangZoneStopFlash` in `src/client/net/scriptrpc.cpp` (around lines 1487–1537). The destructor and constructor are used by the pool lifecycle (`src/client/net/netgame.cpp`, allocation/reset paths).

- **MATCH — constructor, source line 12; candidate `FUN_10002150 @ 0x10002150`.** Index body `0x10002150..0x10002177`; complete pseudocode and assembly read. argumentless member constructor: `this` in ECX, no explicit stack arguments; zeroes 0x400 DWORD pointers at `[this+i*4]` and 0x400 active DWORDs at `[this+0x1000+i*4]`; returns `this` by constructor ABI. Assembly confirms both arrays and exact 1024 iterations. No failure path or callee. Official static callers include 0x10008230 and 0x10008f50. No existing `Official:` mapping found for this VA.
- **MISMATCH — destructor, source line 21; candidate `FUN_10002180 @ 0x10002180`.** Index body `0x10002180..0x100021ad`; complete pseudocode and assembly read. For each of 1024 slots, official calls `_free(pointer)` if nonnull, then clears that pointer; it does not clear the parallel active array here. Source uses `delete zones[i]`, which is incompatible with the `malloc(24)` record allocation in Create. Same iteration and null behavior, but allocator/deallocator family differs. Existing incoming calls include pool destruction paths 0x10009570, 0x10008f50, 0x100084f0. Recommended correction: release these malloc records with `free`, preserving pointer clearing and official active-array behavior. No existing mapping found.
- **MISMATCH — Create, source line 31; candidate `FUN_100021b0 @ 0x100021b0`.** Index body `0x100021b0..0x10002220`; complete pseudocode and assembly read. `__thiscall`: ECX=this; stack WORD id then five 32-bit values (four float bit patterns and DWORD color); callee pops 0x18 bytes. If prior pointer exists, official `_free`s it and clears pointer and active flag; calls `_malloc(0x18)`; on allocation failure leaves slot null/inactive and returns void; on success stores rectangle words in order `[minX,maxY,maxX,minY]`, color twice, pointer, active=1. Source field order and allocation-failure handling match, but it later releases the malloc-owned object with `delete` in this function's replacement branch and in Delete/destructor. This is a C/C++ allocation-family contract mismatch; do not excuse it based solely on a common underlying heap implementation. Correct all three release sites to `free` (or consistently change allocation, only if official allocation failure and layout behavior remain equivalent). Official incoming caller is 0x1001cb40 / ScrGangZoneCreate. No existing mapping found.
- **MATCH — StartFlashing, source line 52; candidate `FUN_10002230 @ 0x10002230`.** Index body `0x10002230..0x10002245`; complete pseudocode and assembly read. `__thiscall` id is zero-extended WORD and color is 32-bit; if the slot pointer is nonnull, writes color at record offset 0x14; otherwise no-op; void return, callee pops 8 bytes. Assembly agrees. Incoming caller 0x1001cd10 / ScrGangZoneFlash. No existing mapping found.
- **MATCH — StopFlashing, source line 58; candidate `FUN_10002250 @ 0x10002250`.** Index body `0x10002250..0x10002268`; complete pseudocode and assembly read. `__thiscall`, WORD id; if the record exists, copies base color at +0x10 to flash color at +0x14; otherwise no-op; void return, callee pops 4 bytes. Assembly agrees. Incoming caller 0x1001cdd0 / ScrGangZoneStopFlash. No existing mapping found.
- **MISMATCH — Delete, source line 64; candidate `FUN_10002270 @ 0x10002270`.** Index body `0x10002270..0x1000229f`; complete pseudocode and assembly read. `__thiscall`, WORD id; if pointer nonnull, official `_free`s it and clears pointer and active DWORD; null is no-op; void return, callee pops 4 bytes. Source uses `delete` on the malloc-owned `GangZone`, mismatching the allocator contract. Recommended correction: use `free` and preserve the exact clearing order/effects. Incoming caller 0x1001cc60 / ScrGangZoneDestroy. No existing mapping found.
- **ALREADY MAPPED — Draw, source line 74; candidate `FUN_100022a0 @ 0x100022a0`.** Index body `0x100022a0..0x10002307`; complete pseudocode and assembly read. `__fastcall`, this in ECX; calls GetTickCount, toggles byte phase and stores new tick when signed `(now-tick) >= 500`, then scans 1024 active slots and calls the draw helper with the record pointer and either flash or base color. Source's signed LONG threshold, phase update, active scan, and color selection agree with the owner. Real caller is the clone's `CGangZonePool::Draw` hook path (`src/client/game/hooks.cpp`, line 2591); the parent independently confirmed an existing `Official: FUN_100022a0 @ 0x100022a0` at `src/client/win/game_runtime.cpp:752`. Do not count this imported body again; it is not a duplicate-body mismatch, just an already claimed unique official entry.

## Mapping and exclusion audit

Searches for every candidate VA across `src/` found only one existing Official mapping among these entries: 0x100022a0 in `src/client/win/game_runtime.cpp:752`. This is why that exact Draw body is ALREADY MAPPED and cannot add a unique count. No existing Official mapping for the remaining exact candidate starts was found. The source helpers inspected here are ordinary class methods with exact independent official owners; none is a template, macro, lambda, generated body, or standalone helper to exclude. `Get` is retained as unresolved rather than excluded because its source body is real but its exact official owner is unproven.

## Caveats and recommended follow-up

The three GangZone mismatches all trace to one paired-allocator defect: official Create allocates with `_malloc`, while clone replacement, Delete, and destruction use C++ `delete`. Change those release calls to `free`, then re-audit the three bodies and real RPC paths before any count change. The TextDraw Create allocation branch was resolved by inspecting the official new-handler path; do not treat the explicit null checks as evidence that modern throwing `new` diverges. No conclusions here extend beyond the two assigned files or the bounded set of 15 bodies.
